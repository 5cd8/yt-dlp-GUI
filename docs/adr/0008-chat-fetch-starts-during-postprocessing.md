# ライブ以外のチャット取得は、動画取得の後処理の間に別プロセスで始める

ライブ以外のYouTube・Twitchでチャットリプレイを取るときは、動画取得のyt-dlpが、ダウンロード後の後処理（マージ・メタデータ付与・サムネイル埋め込み・保存先への移動）に入った時点で、チャット取得を別のプロセスとして始める。合図は、yt-dlpの標準出力の行頭が `[Merger]`・`[ExtractAudio]`・`[Metadata]`・`[EmbedThumbnail]`・`[MoveFiles]`・`[VideoRemuxer]`・`[VideoConvertor]`・`[Fixup…` のどれかである行（`PostProcessingChatFetch.IsPostProcessingLine`）。動画取得が終わるまでにチャット取得が終わっていなければ、段階表示 `チャット取得中` を出して待つ。合図を検知できなかったときは、従来どおり動画取得の後に始める。YouTubeのチャットは、動画取得のyt-dlpには付けず、チャットだけを別のyt-dlp（`--skip-download --write-subs --sub-langs live_chat`、ライブの録画後と同じ `LiveChatReplay.BuildDownloadArgs`）で取る。Twitchは従来どおり TwitchDownloaderCLI。ライブ録画は対象外。

理由は、後処理の間はダウンロードをしておらず、通信が空いているため。さらにYouTubeは、動画取得と同じyt-dlpにチャットを任せると、字幕が動画のダウンロードより先に取られ（2026-10-16、yt-dlp 2026.08.19で確認。`There are no subtitles for the requested languages` が `[download] Destination:` より前に出る）、チャットを取る時間の分だけ動画のダウンロードの開始が遅れていた。

## Considered Options

- 動画のダウンロードと同時にチャットも取る: 帯域を取り合う。ダウンロードしていない時間を使う、という目的から外れるため却下。
- ライブ録画も対象にする: YouTubeは録画の直後にチャットリプレイがまだ用意されていないことがあり（ADR 0005）、早く始めても取れる見込みが増えない。仕上げ（ffmpeg）が出力ファイル名を書き換えるので、チャットのファイル名を先に確定させることもできない。Twitchのライブは、従来どおり動画取得の後に取る。
- 絵文字キャッシュ投入も前倒しする: チャット取得が終わるのは動画取得の完了の前後で、効果が小さく、ステータスの扱いが増えるため却下。
- 動画取得のyt-dlpにチャットを任せたまま、絵文字キャッシュ投入だけを前倒しする: Issue #41 の要件（チャット取得を後処理の間に始める）と違い、字幕が動画より先に取られる問題も残るため却下。

## Consequences

- ADR 0002（Twitchは逐次）の「1キュー項目＝1プロセス」という前提は、ライブ以外では崩れる。並行して動くのを後処理の間の1プロセスに限り、専用のスロット（`ActiveChatCts`・`ActiveChatProcPid`）に入れ、中止を `CancelItemWork` に集め、チャット取得の失敗を実行ログへの警告にとどめる（ADR 0001）ことで、複雑さを抑えた。ステータスを決めるのは、今までどおり動画取得の成否だけ。
- 動画取得が失敗・キャンセルしたときは、並行して動いているチャット取得も止める。「失敗」は、再試行を使い切った最後の失敗を指す。先に終わっていたチャットのファイルは残る。Twitchは「失敗を再キュー」すると、`MakeUniquePath` で `<名前>.chat_replay(1).json` ができて重複しうる。受け入れる。
- 動画取得を再試行するとき、1回目の試行の後処理で始めたチャット取得は動き続け、2回目の動画のダウンロードと並行する（1項目につき1回だけ始める）。リトライの待ち時間の間に「選択を中止」すると、チャット取得だけが止まり、動画取得のリトライは続く（既存の隙）。チャット取得は取り直さないので、動画取得がその後に成功してもチャットは取れない。
- 後処理の行のタグはyt-dlpの仕様に依存する。変わったら、フォールバックで従来どおりの順になるだけで壊れないが、短縮は効かなくなる。
- yt-dlpを `Kill` で止めると `%TEMP%\_MEI*` が残る。動画取得の失敗・キャンセル・項目の中止のたびに、動いているチャット取得のyt-dlpを止めるので、残る場面が増える（従来は右クリックの取得を止めたときだけ）。
- 動画取得が `ダウンロード完了` になってから `チャット取得中` を出すまでの一瞬に「完了項目を削除」を押すと、`CancelItems` を通らないためチャット取得は止まらず、自然に終わるまで走る。従来のTwitchにもあった隙で、受け入れる。
- 2つのyt-dlpが同じ `--cookies` ファイルを同時に使う。この状況は、チャンネル事前投入（`ChannelPrefetchTools`）がキュー処理と並行して動くことで既に存在する。ただし、チャンネル事前投入は手で始める時々の操作で、今回はcookieを使うチャットONの項目のたびに起きる。実行の前後でcookieファイルを比べて確かめる（前後比較では、ほぼ同時に終わったときの書き込みの競合は再現できない。起きやすいのは、後から終わる動画取得のyt-dlpが、チャット取得側の更新を上書きして失うこと。推測）。実害があれば、チャット取得のyt-dlpにcookieファイルのコピーを渡す。
- ライブ以外のYouTubeでチャット取得をONにすると、チャットの無い動画でも、毎回yt-dlpが1つ追加で起動する（denoでの抽出を含む）。後処理の時間より長いと、`チャット取得中` が数秒出る。従来は動画取得のプロセスの中で済んでいた。
